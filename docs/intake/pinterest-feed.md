## System in three lines
Visual discovery feed where each user's home feed is materialised in HBase (through the Zen graph service) by SmartFeed workers that pull candidate pins from follow, interest and recommendation sources, score them with Pinnability ML, and store ordered feeds for cheap reads. Recommendations come from Pixie, an in-memory random walk over a pruned 3-billion-node pin-board graph held on single 244 GB machines; core objects live in a 4,096-shard MySQL fleet with ids that encode the shard; async work runs on PinLater then Pacer. Hard because feed generation is write-heavy fan-in, graph recommendations must answer in tens of milliseconds, and job queues at billions per day suffered lock contention and noisy neighbours.

## Scale (only if stated)
- Users / DAU: 200M+ users, 3B+ items (Pixie paper)
- Requests per second: Pixie ~1,200 recommendations/sec per server, ~100,000/sec cluster; p99 under 60 ms
- Data volume: graph 7B nodes and 100B+ edges pruned to 3B nodes and 17B edges in ~120 GB RAM; MySQL 4,096 shards initially, expanded to 8,192 (16-bit shard id space of 64K)
- Message throughput: PinLater "billions of job executions on a daily basis", "millions of jobs each minute"; Pacer dequeue latency under 1 ms
- Impact: "systems backed by Pixie contribute to more than 80% of all user engagement on Pinterest"
- Goku: last 24 h in memory (Gorilla engine, 12x compression), longer term on disk

## Failure modes, incidents, tradeoffs the source discusses
- Cross-machine walks are the enemy: "Random walk does not have to cross machines which brings huge performance benefits"; whole graph on one box. Source: Pixie paper.
- Pruning trade: six times smaller graph and better quality, but aggressive pruning "risks discarding relevant edges". Source: Pixie paper.
- Early stopping halves runtime with "high overlap" to full walks. Source: Pixie paper.
- Daily rebuild: graph load ~10 minutes, servers restart daily; freshness bounded to one day. Source: Pixie paper.
- PinLater lock contention: every Thrift server scanned every shard; "More than half of all database queries returned empty results". Source: bytebytego citing Pinterest.
- Noisy neighbours: image processing and email jobs shared workers; crashes hit all queues. Source: bytebytego citing Pinterest.
- FIFO impossible across shards; Pacer offers FIFO only with single partition. Source: infoq.
- Pacer: exclusive partitions per broker via Helix, in-memory prefetch, per-queue Kubernetes pods; MySQL still the backing store. Source: infoq.
- MySQL sharding: ids encode shard so routing needs no lookup; shard count doubled by adding servers for ids 4,096-8,191; no cross-shard joins by design. Source: sharding post via search summary.
- Home feed: HBase chosen as materialised feed backend; workers write, reads are cheap scans. Source: home feed post via search summary.
- Goku: moved from push to shard-aware pull with a second Kafka topic to protect storage from ingestor bursts. Source: Goku posts via search summary.
